**Status:** FROZEN FOR CURRENT EXECUTION

**Purpose:** keep engineering effort aligned with the evidence produced by GALACTIC → DISCOVER → ABSTRACT → GRAVITY → REALITY CHECK.

## 1. Current strategic split

AutoPulse operates on two independent tracks:

```text
TRACK A — CORE CERTIFICATION
truth + reliability + compatibility + physical evidence

TRACK B — PRODUCT VALIDATION
recurring problems + repair lifecycle + Before/After + Vehicle Memory hypothesis
```

Track B must not force unvalidated production architecture into Track A.

## 2. Priority classes

- structured runtime/flight-recorder observability;
- Live runtime reliability;
- Check reliability;
- shared evidence invariants;
- compatibility truth.

P0 beats feature expansion.

### P1 — Current Core

- Live;

- Session Summary;

- minimal Intervention record;

### P4 — Out of current scope

## 6. Release rule

A release is justified by improved trust/certification, not by feature count.

Every candidate should answer:

- what became more trustworthy?
- what exact artifact was tested?
- what physical tuple was exercised?
- what blocker closed?
- what compatibility claim gained evidence?

## 7. Promotion rule

A capability moves from P2 to P1 only with convergent behavioral evidence.

Vehicle Memory / Before-After require, at minimum:

- repeated real user pain;
- actual repair follow-up;
- actual prior-history reuse;
- acceptable repair-entry friction;
- evidence that comparison improves understanding/decision-making;
- acceptable hardware onboarding;
- some credible willingness-to-pay behavior.

## 10. Strategic objective

AutoPulse does not optimize for the number of things it can do.

It optimizes first for:

> How much of what the app says can we prove?

Then:

> Does that proven information change a user's decision?

Only after those two answers:

> What deserves to be built next?
